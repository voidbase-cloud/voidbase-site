PocketBase Site
======================================================================

This is the PocketBase Site (aka. https://pocketbase.io), built with SvelteKit.


## Development and contribution

Download the repo and run the appropriate console commands:

```sh
# install dependencies
npm install

# start a dev server with hot reload at localhost:5173
npm run dev

# or generate production ready bundle
npm run build
```


## Deploying to GitHub Pages

Source code lives on `main`. The built site lives on a separate `gh-pages`
branch that GitHub Pages serves, so build output never enters the source
history.

`.github/workflows/deploy.yml` runs on every push to `main`/`master` (or
manually via *Run workflow*): it builds into `build/` and force-pushes that
directory to `gh-pages` as a single orphan commit.

One-time setup in the GitHub repo, after the first workflow run has created
the branch: **Settings → Pages → Build and deployment → Source: Deploy from a
branch → Branch: `gh-pages` / `/ (root)`**.

The site is served at **voidbase.cloud**: the workflow writes the `CNAME` file for GitHub Pages, the zone on Cloudflare needs
A/AAAA records for the apex pointing at GitHub Pages (185.199.108-111.153, 2606:50c0:8000-8003::153, DNS only), and the
backend lives at api.voidbase.cloud (`PB_VB_URL`).

The site uses root-absolute links and asset paths (`/docs`, `/images/...`,
`/fonts/...`), so it must be served from the domain root. That means either:

- a user/organization site repo named `<owner>.github.io`, or
- a project repo with a **custom domain** configured under Settings → Pages.

Deploying a project repo without a custom domain (served under
`https://<owner>.github.io/<repo>/`) will break those links.

Notes:

- `static/.nojekyll` is required so GitHub Pages does not drop the `_app/`
  directory.
- `static/pagefind` (the docs search index) is gitignored and regenerated by
  `npm run build`, which also copies it into `build/pagefind`. In local dev the
  docs search only works after you have run a build at least once.

## The Cloud page (`/cloud`) and the backend (`vb/`)

`/cloud` lets a visitor sign in with Cloudflare and create or delete voidbase instances in their own Cloudflare
account with one click. It is a static page; everything happens against the site's own voidbase backend in
[`vb/`](vb/README.md#voidbase-cloud-the-cloud-pages-backend), which is itself one of those instances (an admin can
delete it from the page).

The page talks to `PB_VB_URL` (`.env` for local dev, `http://127.0.0.1:8090`; the Pages workflow reads the
`PB_VB_URL` repository variable under Settings > Secrets and variables > Actions > Variables). `bun run dev` in
`vb/` starts the backend locally; see its README for the Cloudflare OAuth client and release setup.
